# 계약 기반 FE·BE 협업

FE와 BE를 한 사람이 AI 에이전트 두 세션으로 병행했다. 두 세션이 서로의 코드를 읽지 않고도 어긋나지 않으려면, 만나는 지점이 파일 하나여야 했다.

## 문제

- BE가 아직 만들지 않은 API를 FE가 추측해서 구현하면 나중에 전부 다시 쓴다.
- FE 세션이 BE 레포의 코드나 `.planning/`을 읽기 시작하면 두 세션의 맥락이 섞이고 문서가 정본이 아니게 된다.
- 응답 타입을 손으로 쓰면 스펙과 타입이 조용히 어긋난다.

## 결정

**`openapi.yaml`이 API의 유일한 진실이다.**

| 규칙 | 내용 | 근거 |
| --- | --- | --- |
| 생성 | BE가 springdoc로 노출한 스펙을 커스텀 Gradle 태스크 체인으로 파일에 고정. API가 바뀌면 재생성해 커밋 | D-029 |
| 소비 | FE는 `pnpm api:types`로 `schema.d.ts`를 생성하고 그 타입만 쓴다. 수기 API 타입 금지 | FE CLAUDE.md |
| 공백 | 스펙에 없는 API는 구현하지 않는다. `.planning/BE-CHANGE-REQUESTS.md`에 요청·근거·FE 임시 대응·해소되면 할 일을 적는다 | FE ROADMAP 성공 기준 5 |
| 에러 | FE는 응답의 `code` 필드로만 분기. 값 목록은 `error-codes.md`가 계약 | D-017, D-076 |
| 읽기 범위 | FE 세션은 BE의 `docs/`만 읽는다. BE의 `.planning/`과 코드는 읽지 않는다 | FE PROJECT.md |

로드맵도 계약에 종속시켰다. FE M4(예약)와 M5(운영)는 BE가 계약을 갱신할 때까지 대기시키고, 그 사이 M1~M3를 먼저 끝냈다. 추측 구현이 사라진 대신 대기가 생겼고, 대기는 선행 작업으로 메웠다.

| ID | 요청 | FE 임시 대응 | 결과 |

임시 대응마다 "해소되면 무엇을 되돌리는가"를 같이 적어 우회 코드가 영구화되지 않게 했다. 해소된 3건은 같은 날 `pnpm api:types` 재생성 후 되돌렸다.

## 검증

- 계약 밖 호출 감사를 세 표면(앱 코드, MSW 핸들러, E2E 스텁)에서 돌린다. 2026-08-31 40경로 기준 0건, 2026-09-01 41경로 기준 0건.
- MSW `onUnhandledRequest: 'error'`로 Vitest·Storybook에서 계약 밖 요청이 즉시 실패한다 (D-143).
- v1.0 회고 기록: 계약 밖 호출 0건, 재작업 0건.
