# 계약 기반 FE·BE 협업

FE와 BE를 AI 세션 두 개로 병행했습니다. 두 세션이 서로의 코드를 읽지 않고도 어긋나지 않으려면 만나는 지점이 파일 하나여야 했습니다.

## 문제

- BE가 아직 만들지 않은 API를 FE가 추측해서 구현하면 나중에 다시 씁니다.
- FE 세션이 BE의 코드나 진행 상태를 읽기 시작하면 두 세션의 맥락이 섞입니다.
- 응답 타입을 손으로 쓰면 스펙과 타입이 조용히 어긋납니다.

## 결정

`openapi.yaml`이 API의 유일한 진실입니다.

| 규칙 | 내용 |
| --- | --- |
| 생성 | BE가 Gradle 태스크로 스펙을 파일에 고정하고, API가 바뀌면 재생성해 커밋 (D-029) |
| 소비 | FE는 `pnpm api:types`로 생성한 타입만 사용. 수기 API 타입 금지 |
| 공백 | 스펙에 없는 API는 구현하지 않고 BE 변경 요청 문서에 요청·근거·임시 대응·되돌릴 방법을 기록 |
| 에러 | FE는 응답의 `code` 필드로만 분기. 값 목록은 `error-codes.md`가 계약 (D-017, D-076) |
| 읽기 범위 | FE 세션은 BE의 `docs/`만 읽고 코드와 `.planning/`은 읽지 않음 |

로드맵도 계약에 종속시켰습니다. FE의 예약·운영 화면은 BE가 계약을 갱신할 때까지 대기시키고 그 사이 기반·회원·관리자 화면을 먼저 끝냈습니다.

## 실제로 돈 기록

| 요청 | FE 임시 대응 | 결과 |
| --- | --- | --- |
| 관리자용 회원 이력 조회 | 컴포넌트와 fixture 스토리로만 고정, API 호출·목 없음 | 해소 (D-149) |
| 내 예약 목록 기간 필터 | 오름차순 마지막 페이지 조합으로 계약 안에서 우회 | 해소 (D-150) |
| 출석 명단에 전화번호 | 이름만 표시, N+1 보강 금지 | 해소 (D-148) |
| 오류 응답 스키마 · 관리자 me · 예약 단건 조회 | 런타임 타입가드 · 토큰 존재 판정 · 현 동작 유지 | v1.1 백로그 |

해소된 3건은 같은 날 타입을 재생성하고 우회 코드를 되돌렸습니다.

## 검증

- 앱 코드, MSW 핸들러, E2E 스텁 세 표면에서 계약 밖 호출을 셉니다. 41경로 기준 0건.
- MSW가 계약 밖 요청을 에러로 처리해 Vitest·Storybook에서 즉시 실패합니다 (D-143).
- v1.0 회고 기준 재작업 0건.
