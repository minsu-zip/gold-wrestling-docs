# 동시성 제어

정원 마지막 자리와 1:1 레슨 슬롯에서 동시 예약이 들어와도 초과 예약이 0건이어야 한다. 이 요구는 `policies.md` §8에 먼저 적혔고, 구현은 그 문장을 만족시키는 쪽으로 결정됐다.

## 문제

- 예약제 수업은 정원 10명, 1:1 레슨은 타임당 1명이다. 마지막 자리에 두 요청이 같은 순간 들어온다.
- "조회해서 자리가 있으면 저장"은 조회와 저장 사이에 다른 트랜잭션이 끼어든다. 애플리케이션 조건문으로는 막을 수 없다.
- 운영 서버가 다중 인스턴스가 되면 JVM 안의 동기화는 무효다.

## 결정

**DB 제약과 조건부 갱신을 먼저 쓰고, 락은 부족한 지점에만 쓴다** (D-021).

| 경쟁 지점 | 방어 | 왜 이것인가 |
| --- | --- | --- |
| 1:1 레슨 슬롯 | `(session_id)` 부분 유니크 제약 | 코드 경로가 몇 개든 DB가 마지막 방어선 |
| 예약제 정원 | 조건부 UPDATE/INSERT (남은 자리 > 0일 때만) | 조회-판단-저장 사이의 창을 없앤다 |
| 그래도 남는 곳 | `SELECT ... FOR UPDATE` | 필요한 행에만, 짧게 |
| refresh 토큰 회전 | 조건부 UPDATE + 실패 응답에서도 커밋 | 재사용 감지가 경쟁 상황에서도 남아야 한다 (D-051) |
| 배치 실행 | `batch_execution` `RUNNING` 부분 유니크 인덱스 | 같은 원리를 원장이 아니라 실행 이력에 적용 (D-117) |

기각한 것: 낙관적 락 `@Version`은 충돌 시 재시도가 필요하고 마지막 자리 경쟁에서 재시도가 폭증한다. 애플리케이션 레벨 동기화는 다중 인스턴스에서 무효다.

## 검증

**JVM 동시성 통합테스트로 "정확히 정원 수만큼만 성공"을 증명한다** (D-098). `ExecutorService`와 `CountDownLatch`로 N+M 스레드를 같은 순간에 풀고, 실제 PostgreSQL(Testcontainers) 위에서 성공 건수가 정원과 같은지, 초과가 0인지 센다. 이 방식은 BE `conventions.md` §10.4와 `add-domain-test` 스킬에 규약으로 남아 같은 종류의 테스트가 같은 모양으로 생긴다.

k6 부하테스트는 이 phase에서 넣지 않았다. 목적이 정확성 증명이지 처리량 측정이 아니었고, 새 인프라가 필요했다. 배포 뒤 BE Phase 10에서 실 서버를 상대로 초과 예약 0건과 p95를 다시 실증하고 D-098을 해소하는 결정을 남긴다.
